# AGENTS

## Project

- Name: `skopos`
- Module: `github.com/martinsuchenak/skopos`
- Go 1.27.4 (keep the latest patch: release builds use go.mod's go line), SQLite (modernc.org/sqlite — no CGO), Bun for frontend

## Commands

```sh
task build-local      # build for current OS (runs frontend-build first)
task build            # cross-compile for linux/darwin/windows amd64+arm64
task test             # go test ./... -v -count=1
task lint             # golangci-lint run ./... (every package, tests included)
task check            # the CI gate: fmt:check, vet, lint, test:race
task frontend-build   # bun install --frozen-lockfile && bun run build in web/
task release:check    # goreleaser check + snapshot release in dist/ (nothing published)
task release -- vX.Y.Z  # tags origin/main once CI passed on it and CHANGELOG.md has the section
```

Running a single test package: `go test ./internal/status/... -v -count=1`

The server must be running for MCP/REST integration testing: `go run . serve` (HTTP on :8080, MCP at /mcp).

Live agent-CLI tests are opt-in (they spend tokens): `SKOPOS_LIVE_CLAUDE=1` / `SKOPOS_LIVE_OPENCODE=1 go test ./internal/worker -run TestLive -v` — they define what "verified lockdown" means; re-run them after upgrading an agent CLI. `TestLiveSubagentLockdown` checks a claude subagent (the `Agent` tool, `SKOPOS_LIVE_SUBAGENT_TOOL` for another name) stays in the same lockdown; it asserts from the event stream that the subagent really ran.

User-facing docs: the pipeline tutorial is `docs/guides/pipeline.md`, the worker reference `docs/deployment/worker.md`, config keys `docs/configuration.md` — keep them in step with worker/runner changes.

## Architecture

```
main.go → cmd/register.go → cmd/serve.go
                              ├── cmd/routes/       (HTTP handlers)
                              ├── cmd/mcp/          (MCP tool definitions)
                              └── cmd/              (CLI commands: report, blackboard, plans, worker init|install|check|runner …;
                                                     relay_slack.go = the in-process Slack relay)
internal/
  ├── status/     handler → service → storage   (agent status, sessions, events)
  ├── blackboard/ handler → service → storage   (scoped knowledge entries)
  ├── plans/      handler → service → storage   (plans, items, dependencies, revisions+locking)
  ├── inbox/      handler → service → storage   (workspace inbox: capture → enrich → convert-to-plan, agent-pipeline workflow)
  ├── workspaces/ handler → service → storage   (workspace registry, auto-register)
  ├── events/     in-process SSE hub + middleware (publishes named events on mutations)
  ├── codeindex/  code index (parse → storage → service → handler; per-workspace SQLite DBs)
  ├── install/    skopos install — wires MCP config into AI agent configs (+ Claude Code hook suite in assets/hooks/)
  ├── auth/       principals (root, key, run) + root/scoped API key and run-token auth (Bearer); scoping enforced in services; approver and admin permission gates
  ├── apikeys/    scoped API key domain (handler → service → storage; sk_ keys, sha256-hashed; workspace groups)
  ├── audit/      append-only mutation log (actor/via rendering, entity index, scoped reads; plan 01a0bf7c)
  ├── approvals/  append-only approvals tied to immutable subjects (plan revision+base, review head)
  ├── itemstate/  GET /api/inbox/{id}/state: an item's state for other systems (composes inbox, plans, runs, qa)
  ├── idempotency/ Idempotency-Key middleware on POST /api/inbox… (idempotency_keys, 24h, per API key)
  ├── runs/       run queue: stages, affinity leases, chaining (agent-pipeline lean 1b); per-attempt run tokens; the claim's runner + policy decision
  ├── policy/     runner policy, pure: allow rules, runner facts, layers, provider derivation
  ├── confrev/    append-only revisions of policy and configuration (config_revisions + config_heads)
  ├── wsconfig/   workspace config (stage capabilities among it), runner and wrapper definitions on the server (handler → service; revisions in confrev, config_effective)
  ├── secretbox/  the server's secret key: key ring (current + previous), sealed secret store (`secrets`), rotation over every sealed table
  ├── fleetfile/  the run configuration as one document: export, plan, apply (skopos config export|apply)
  ├── worker/     `skopos worker`: execution plane — claim/execute/report loop, runners (claude, opencode, command), lockdown, profiles, knowledge (AGENTS.md/skills at base), account pool, probes
  ├── notify/     notification module: provider interface (Slack Socket Mode first)
  ├── logship/    log output: an io.Writer for a JSON logger that batches + POSTs (ndjson/loki/elasticsearch/raw)
  ├── health/     background goroutine: stuck-agent detection
  ├── cleanup/    background goroutine: data retention cleanup
  ├── db/         SQLite connection + schema.sql migrations
web/              Alpine.js + Tailwind CSS, embedded via go:embed, Bun build
```

Every domain package follows `handler → service → storage` layering. Storage uses raw `*sql.DB`. Services are interface-based for testability.

## Key Patterns

- Commands self-register via `init()` in `cmd/` using `Register()`.
- Routes self-register via `init()` in `cmd/routes/`.
- `go-scaffolder:` comments are patch markers — do not remove them.
- Add new CLI commands, API endpoints, or MCP tools with `go-scaffolder add` where possible.
- All IDs are UUIDv7 (text, time-sortable).
- DB timestamps go through `internal/dbtime` (fixed-width UTC text: text order = time order); never `Format(time.RFC3339Nano)` into SQLite. New tables use INTEGER Unix ms instead. Versioned migrations / typed rebuilds of the old tables are planned after the multi-agent feature is polished (tmp/db-types — review.md).
- Config: TOML (`skopos-config.toml`, gitignored — copy from `skopos-config.example.toml`; optional, falls back to flag defaults + env) + env var overrides (`SERVER_PORT`, `SKOPOS_API_KEY`, etc.).
- Frontend assets are embedded in the binary via `web/embed.go`. Run `task frontend-build` before `task build` (the build task depends on it automatically).
- `task lint` sets `GOCACHE` to a local directory — don't run bare `golangci-lint`.
- The dashboard subscribes to `/api/events/stream` (SSE) for real-time updates; the `events` package's middleware publishes named events on successful mutations.
- Logs: `serve`/`worker` log to stdout and, with `--log-output-url` (global `--log-output-*` flags, env `LOG_OUTPUT_*`, config `log.output.*`), to an HTTP log intake through `internal/logship` — the way knot wraps paularlott/logger: the writer plugs into the logger's JSON handler; paularlott/logger itself stays unchanged. With an output set, stdout is JSON. The worker keeps log/slog.
- SRV URLs (internal/srvurl): any URL may be `srv+http(s)://name/path` (knot's convention). `srvurl.Install()` (main.go) registers both schemes on `http.DefaultTransport`, so every client built on it handles them — keep new clients on the default transport (no custom `Transport`). The host stays `name` (TLS SNI); each new connection re-resolves and tries targets in RFC 2782 order. Global `--dns-server` (`SKOPOS_DNS_SERVER`; the worker re-reads it after its env file). Anything handed to another program must go through `srvurl.Resolve` (agent MCP config — rewritten per run via `EnableAgentMCP` refresh; `pushBranch`; `skopos install` agent entries). URL validators accept `srvurl.HTTPScheme`. One exception: the webhook dispatcher (`integrations.newClient`) has its own Transport, because its dial-time check refuses private addresses after DNS (request forgery); webhook URLs are https/http only, never `srv+`.
- Run logs (internal/worker/runlog.go → `POST /api/runs/{id}/log` → `run_logs`, internal/runs/logs.go): `execute` opens a per-run `runLog` carried in the context (`withRunLog`/`runLogFrom`, nil = no-op); runners tee stdout/stderr through `teeOutput` with a per-runner event formatter (`claudeEventLines` — claude runs with `--output-format stream-json --verbose`, result read by `claudeResultCatcher`; `opencodeEventLines`; `codexEventLines`), `runShell` tees setup/check output (`withLogSrc`), `runAgent`/`report`/pauses add worker notes, and slow steps before the agent (clone wait in `holdClone`, parking, fetch/checkout, setup skipped) go through `runLog.stepf` (a second line with the duration when ≥5s). Every line goes through `w.redactor()` (worker keys via `AddSecrets`, push tokens, env-file values, account credentials). The endpoint authorises by worker + key + lease hash in any status (lines follow the report), but a retry requeue clears the lease, so `report` and pauses `flush()` first. Storage: one gzipped batch per row, 8 MB cap per run (`MaxRunLogBytes`, marker line), dropped by the cleanup retention. Readers long-poll (`?wait=`, ≤25s; `logSignal`/`logStored` wake only that run's readers — no SSE broadcast); the dashboard panel (`openRunLog`, `pollRunLog`, `stepLogs`) reads `?tail=` (newest batches only, `LogTailRows`) then `?after=<cursor>&wait=25` while live. Claude failures are classified only from stdout outside the event stream plus stderr (`claudeResultCatcher.plainText`) — tool output must never decide the outcome; an agent event over 32 MB is left out with a note, never sent raw. Records with the run's ids also go to the log output (`SetLogOutput`).
- Dashboard markup: shared structure lives in `web/templates/partials.html` (`modal-open`/`modal-close` dialog shell, `checklist`, `ws-badge`, `index-branch`; `dict` builds the params). Status colours go through `toneOf(kind, value)` → `.tone-*` classes in `style.css` (defined once per theme) — never hand-written `bg-x-500/15 text-x-300` pairs. `TestDashboardIDsAndDialogLabels` guards ids and dialog labels.
- Workspaces are strict-scoped: blackboard entries and plans require an exact `workspace_id` match when filtered — and writes require `workspace_id` for every principal (root included). Unscoped reads for a scoped key return exactly its slice; by-id access to foreign objects 404s. Session-derived workspaces are auto-registered (system privilege) so they persist.
- API keys: root key from config + DB-backed scoped keys (internal/apikeys). The principal travels in the request context (internal/auth, ctxkeys.PrincipalKey); nil principal = internal/background caller (registrar, health ticker, refresher).
- Workspace groups: a key's scope = explicit workspaces + group members + registered workspaces matching group `path.Match` patterns. Resolved inside `LookupKey` on every request (no cache); scope changes and pattern-matching workspace registrations drop the affected keys' SSE streams. Root-only management (`skopos group …`, `/api/groups`); `skopos key who-can <workspace>` is the reverse query.
- Key capabilities (tmp/agent-mcp-and-indexing — design.md §1): a scoped key may carry `api_keys.capabilities` (JSON; NULL = full access) — surfaces `rest`/`mcp` and areas `code|blackboard|plans|inbox|status|runs|workspaces|events` `:read|:write`. `auth.Authenticator.Middleware` refuses a capped key outside them (route prefix → area via `auth.RouteCapability`, fail closed for unmapped routes; `/api/whoami` always); MCP: `cmd/mcp/capabilities.go` `toolNeeds` (every tool must have an entry — `TestEveryToolHasCapabilityNeeds`), `filterToolsList` hides/refuses at the protocol level, `guardTool` (in `registerTool`) covers `execute_tool`. Presets in `auth.Presets` (`agent`).
- External systems (tmp/integrations — design.md, phase 1; guide docs/guides/external-systems.md): `POST /api/inbox` takes `start` (queue|review — approver checked before the create; a failed start returns the open item with `start_error`) and `external_url` (https only, `NormalizeExternalURL`); `GET /api/inbox?ref=` (`ListFilter.Ref`, exact); `GET /api/inbox/{id}/state` (internal/itemstate, served through `inbox.Handler.SetStateHandler` so the route stays in inbox_routes.go: turn, gate, brief, plan revisions at the gate, open questions, newest implementation, reviews of the newest reviewed head (`runs.ReviewPassed` / `runs.BlockingFindings` — the one pass rule), run in progress (interrupted counts), reason from the current round only; plan needs plans:read and the run sections runs:read for a capped key; `actions` = endpoint names, empty without approver, second-opinion by `inbox.SecondOpinionHead` — the rule the request checks). `internal/idempotency` wraps `/api/inbox` POSTs after auth (owner = key id; the hash covers method, path, query, on-behalf-of person and body; 422 other request, 409 running; only <400 responses kept; abandoned after 5 min; pruned by cleanup). Key `delegate` flag + `X-Skopos-On-Behalf-Of` (validated in `auth.Middleware`, refused 400 for other keys) → `Principal.OnBehalfOf`; every actor rendering goes through `auth.Actor` ("<person> (key <name>)"), `audit_log.on_behalf_of`. Preset `integration` (+ events:read). Phase 2 (internal/integrations): `integration_events` (STRICT, seq AUTOINCREMENT = feed cursor) written through `Emitter.Emit(ctx, db, …)` inside the producer's transaction — inbox `emitStatus` (status_changed + needs_you/plan.ready/closed) in transitionWith and every manual status path, `item.created` in CreateItem's tx, runs `startedEvent` in the Claim tx and `finishedEvents` in Report's tx (now a tx), qa sets/answers in InsertRecord's tx; `insert` adds the item's workspace/ref/external_url/status by query. Webhooks: `webhooks` (secrets AES-GCM under `integrations.secret_key`; none = webhooks off, feed on), `webhook_deliveries`, `webhook_attempts`; `Dispatcher` (serve goroutine, 2s tick + emit wake): fan-out from `cursor_seq` (disabled hooks don't fan out), per-item order, 4 in flight per hook, Standard Webhooks `Sign`, retry schedule 5s…10h (8 attempts), 410 or a 72h run of failed attempts disables (a success, or 12h without a failure — `failureGap`, `last_failure_ms` — ends a run; audited `webhook.disable` via system); proxies not used; SSRF: https or `allow_http` hosts, `newClient` dial Control refuses private/loopback/link-local/CGNAT outside `allow_private`, no redirects, no proxy. Management `/api/webhooks` (routes registered via `RegisterIntegrations` init + `MountIntegrations`; area events): root, or approver for workspaces in scope (groups root-only), audited `webhook.*`. Feed `GET /api/events` (scoped, long-poll ≤25s, 410 `oldest_seq` when the cursor was pruned). `integrations.Prune` in cleanup keeps events a hook still has to fan out or deliver. Dashboard `/?item=<id>` opens the item. Phase 3: dashboard Webhooks view (`webhooks`, `canApprove()`; the secret dialog is shared with API keys via `showSecret(kind, …)`), `Service.SetDisableNotifier` → relay `PostWebhookDisabled` (URL without query); an old secret the key can't open is left out of the signatures. Role-gated static page elements carry `data-role="root|approver"` + `style="display: none"` and are shown by `syncRoles()` after `fetchWhoami` — never `x-show` (it applies changes in the next animation frame, and where frames don't run the Keys item stayed hidden); `isRoot`/`isApprover` flags serve x-show inside dialogs.
- Approver permission: `auth.RequireApprover` gates the inbox workflow's human actions; root and nil (internal) pass, plain scoped keys get `ErrApproverRequired`. Agent and worker keys never hold it.
- Admin permission (tmp/central-config — design.md, phase 0): `api_keys.admin` → `Principal.Admin`; `auth.RequireAdmin(ctx, ws)` (the workspace in scope), `RequireAdminAll(ctx, workspaces)` (a group: every member in scope; empty = fleet), `RequireFleetAdmin` (the key reaches all workspaces). Root and nil pass every level; a run principal never. It gates policy and configuration changes (use it, not `RequireRoot`, for anything new of that kind). Granted by root only (`skopos key create|edit --admin`); `worker.CheckWorkerKey` refuses a worker key that holds it. `Principal.Kind()` = system|root|key|run. Key and group changes are audit events (`internal/apikeys/audit.go`: `key.create|update|revoke|delete`, `group.create|update|delete`, via from `apikeys.WithVia`).
- Agent-pipeline workflow (docs/design/agent-pipeline.md): inbox statuses + frozen transition matrix in `internal/inbox/models.go` — human actions approver-gated, system transitions (`/api/inbox/{id}/transition`) executor-only; every transition audit-logged; workflow items never change workspace, and past the plan gate (status approved+ or a recorded plan approval) title changes and content rewrites are approver-only (appends keeping the content as a prefix stay open — the worker's verdict/amendment/enrichment sections) — every workflow-item edit is audited (`inbox.edit`); retry answers append inside the transition's transaction; `plan_revisions` lock on approve (structural edits then 409 `ErrRevisionLocked` until an amendment); approvals name immutable subjects (`<revision>+<base_sha>` / `<head_sha>`). One-time cutover: `skopos inbox migrate-workflow`.
- Multi-agent stages (opt-in; tmp/multi-agent-stages — design.md): `--run-stage ws:review=focus@runner,…` (review/qa) opens a **group** (`run_groups`, STRICT + CHECKs, Unix-ms times; partial unique index = one open group per item+stage). Members are pinned to their own runner (`claimable`); `chain()` hands a member's result to `groupMemberDone`, which decides once (`DecideGroup` is the open→decided transaction) per policy (any-blocks default / majority / all-pass, early-exit, timeout via `SweepGroups`), writes one summary section (`inbox.AppendSection`) and moves the item. Focus briefs `.skopos/focus/<name>.md` are read at the approved base; review findings carry severity (blocking/nit) and the worker enforces fail ⇔ blocking. One runner per stage = unchanged behaviour. Plan groups (`ws:plan=a,b`): the first claimed member's `ensurePlan` hook creates+links the plan; members call `pin-base` then `POST /api/plans/{id}/candidates` (revision with `group_id`/`label`/`candidate_state`, step ids pre-assigned, live items untouched); `ApproveCandidate` materialises the candidate with ITS step ids (hash re-verified), locks it, supersedes siblings — one tx; `LatestRevision` skips superseded candidates; only the newest round's open candidates are approvable. Request-changes with `revision_id` = one seeded single plan run (`QueueSeeded`, pinned to the candidate's runner); without = round N+1. Advisory stages `compare` (judge → `## Comparison`) and `synthesize` (one more candidate, label `synthesis`) run after a plan round with ≥2 candidates when configured (`afterAdvisory`: candidates → compare → synthesize → gate); single runner each, never grouped, and a failure still opens the gate. Per-item switch: `inbox_items.agents` (`panel`/`solo`, NULL = workspace default `--agents-default`, panel when unset) is read by `runs.Queue` via the `SetItemAgents` callback at every queue — solo = one run on the group's first runner, no focus; approver-only + audited on workflow items.
- Runner policy (tmp/central-config — design.md, phase 1a; docs/concepts/runner-policy.md): `internal/policy` is pure — `Rule` (provider/model/kind/runner globs + stages), `Facts` (what a worker reports per runner), `Effective.Allows` (every layer must allow; no layers = allow all), `ProviderForEndpoint`/`ProviderForOpencode` (a LAN host is `unknown:<host>`, never assumed local). Policies are `confrev` revisions (kind `policy`; owners `fleet:ceiling`, `fleet:default`, `group:<id>`, `workspace:<id>`; never updated or deleted). `internal/pipeline/policy.go`: effective = ceiling + (groups + workspace, or the default when none); `SetPolicy`/`ClearPolicy` need `auth.RequireAdmin*` at the owner's level, refuse (`ErrStrands`, 409) what would NEWLY strand a configured runner or drop a workspace's vectors unless forced (`wouldStrand` = stranded after − stranded before), audit `policy.set|delete` (entity `pipeline_policy`); `Prefs` carries the policy (`runs.WorkspacePrefs.Policy`; an unreadable policy keeps the last one, else `policy.DenyAll`); `RunnerAllowed` backs `inbox.SetRunnerPolicy` (a refused second opinion = `inbox.ErrPolicyRefused`, 403 with `reason: policy`). The claim (`internal/runs/policy.go`): `decide`/`decideResume` resolve ONE runner per run (`pinnedRunner`: group member or queued runner without a current preference, else the current preference, else the server picks from the worker's facts order — `runner_picked`, cleared by a requeue and by `releaseForTakeover`), check it with the claiming worker's `ClaimInput.RunnerFacts` in ALL three scans, and write `runner`, `runner_picked`, `policy_rev`, `facts` in the claim UPDATE; a worker without facts gets runs only where no policy applies; an owner's run it may no longer resume becomes a branch takeover; `workerCanTake` and `lastWorkerFor` use the same rules. `workers.runner_info` holds the facts (a change = audit `worker.facts`; `sanitizeFacts` bounds them); claim answers carry `Skopos-Runner-Facts`. `SweepStranded` (in `RunSweepLoop`) marks queued runs no worker may take under the policy (`stranded_ms`/`stranded_reason`, audit `run.stranded` once). Worker (`internal/worker/facts.go`): `Config.RunnerFacts` (claude first, then `worker.runners` order; endpoint from `ANTHROPIC_BASE_URL`/Bedrock/Vertex, `OPENAI_BASE_URL`, the opencode model's provider id or its `baseURL` in the runner's config; `runner_config.<name>.provider|endpoint` declare the rest), `FactProblems` (fatal at startup and in `worker check`: proxy vars in account env, accounts of one runner differing in model/provider/endpoint, a declared provider the endpoint contradicts), `refuseRunner` (a run without a runner, or for one the worker lacks, from a server that reads facts is not run); facts come from `agentEnv` = the scrubbed env an agent really gets (never `os.Getenv` directly: env-file keys are dropped), profile env may not set proxy/endpoint variables, and `pickAccount` drops a run's remembered account and sessions when `run.Runner` no longer matches it (`forgetRun`). Review-found rules to keep: nil prefs must never mean "no policy" (`Claim` takes a resolver so a worker's own run in a workspace it no longer offers is still checked; `Prefs` returns `policy.DenyAll` when nothing is known, and `Effective.Held()` makes the claim hold — neither hand out nor release); a picked runner pins nothing (`pinnedRunner` ignores `runner_picked`); a worker that sends facts but none for a named runner does not have it; cloud customer hosts (`*.amazonaws.com`, `*.azure.com`) are not the cloud's AI service (`awsService`, the Azure AI suffixes); `policy.Contradicts` guards declared providers (runner config and `codeindex.embeddings.provider`, which refuses to start). Embeddings: `codeindex.Service.SetEmbeddingsGate` (allowed, known) is asked in `EmbedPending` (refused = vectors dropped + `ErrEmbeddingsHeld`, which the manager records as neither success nor failure) and `SemanticSearch` (refused = text search only, the query is not sent); serve.go builds the endpoint's facts (`--embeddings-provider` / derived) and matches stage `embeddings`; `pipeline.SetPolicyChanged` re-enqueues affected workspaces.
- Containment as a policy rule (tmp/central-config — design.md, phase 1c; docs/concepts/runner-policy.md#containment): `policy.Rule.Executor` = `isolated` (`wrapper:` and `runner:` classes) | `contained` (those + `host:`) | a glob that starts with a class (`internal/policy/executor.go`: `Isolated`, `Contained`, `ExecutorSatisfies`, `KnownExecutor`, `ExecutorFact`, `ResolveExecutor` — stage+runner > stage > runner > default). `sandbox:<hash>` (Claude Code's sandbox settings) meets NEITHER class — reads stay open by default and the worker's setup/checks run outside it; a rule names it (`sandbox:*`). A host container is never isolation. Worker (`internal/worker/config.go`): `Config.ExecutorFor(ws, runStage, runner)` is the ONE answer to "what contains this run", in order wrapper (named after its profile via `executorName`, hash = argv only) → `SandboxLockdown()` runner (codex, only where `codexSandboxVerified` = macOS, and not for `runsRepoCommands` stages: implement, branch_review) → host (`worker.contained_by`, or an env-only wrapper via `hostWrapper`: `env` with no command of its own, any options) → sandbox settings (runners with `HonorsSettings`) → local; `ExecutorFacts()` (per workspace, compact; `TestExecutorFactsMatchWhatRuns` keeps it equal to `ExecutorFor` for every stage × runner — a second opinion and a branch review use the review profile, `stagePhase`) goes out with every claim (`Client.SetExecutors`, `executors`); `StageProfile.Grants()` (tools, env names, every setting but the sandbox block) is reported apart (`runs.grants`). A REAL wrapper (`wraps()`) goes around the agent AND the worker's setup and check commands of the stage: `withShellWrap(ctx, w.stageShellWrap(run, account, phase))` in the implement stage and before `checkHead`, read by `runShell` (they execute the branch's code; an unprepared wrapper fails the command, never runs it bare). `wrapper.go`: placeholders `{dir} {gitdir} {login} {rundir} {cli} {run} {stage} {workspace}` (`stageWrapper`/`expandWrapper`: one the wrapper uses without a value = `AgentRun.StartErr`; an unknown `{name}` is refused at load; `loginDir` per kind from `agentEnv` or `Account.LoginDir`; a wrapper that uses `{cli}` starts the agent by `WrapBin`, its resolved path), `TempDir` = `<state_dir>/runs/<run>/tmp` for the runners' `MkdirTemp` (removed at run end), `HostContained` (meets the fail-closed grant rule like a wrapper). A run's directory is writable by a wrapped agent, so the worker's own writes there go through `writeNoFollow` (remove + `O_EXCL`: `writeRunLog`, `writeFile0600`) and `runTempDir` replaces a non-directory. `refuseExecutor` (next to `refuseRunner`): the claim's `facts.executor` must equal `ExecutorFor` here or nothing starts. Server: `workers.executor_info` (JSON workspace → facts; `sanitizeExecutors`: offered workspaces only, and a list with ANY entry it cannot keep is dropped whole — a lost override would let the default answer for it; part of the `worker.facts` audit comparison; `ListWorkers` cuts it to the caller's scope), `claimFacts.at(run, runner)` fills `Facts.Executor` for the run's workspace, stage and runner in every decision (no executor facts = no rule with `executor` matches), the claim's `facts` record keeps it; at report `Service.checkExecutor` only decides (may turn the report into a non-retryable failure when the policy does not allow the runner with what really ran) and `recordMismatch` writes `run.executor_mismatch` AFTER the report or requeue was accepted — a report refused for its lease writes nothing; a report without an executor (no agent ran in this attempt) is left alone. Pipeline: `workerFacts.at(stage)` / `byRunner(workers, stage)` resolve the executor per stage for `strandedUnder` and `RunnerAllowed`. The bwrap profile in docs/deployment/worker.md (between the `bwrap-profile` markers; `{gitdir}/config` and `/hooks` read-only) is what `TestBwrapProfileFromDocs` runs (linux, needs bwrap + user namespaces, fixture outside /tmp via `SKOPOS_BWRAP_TEST_DIR`, not in CI) around a stand-in CLI and a check command; it does not prove a real agent CLI works under it.
- Workspace config on the server (tmp/central-config — design.md, phase 2 + 2c; docs/concepts/workspace-config.md): `internal/wsconfig` — `Config` has every field a pointer (nil = not set at this level, an empty list = set to nothing) and is merged, compared and checked through `Fields()` ("push.kind" names). Revisions in `confrev` (kind `workspace_config`, owners `workspace:<id>` / `group:<id>`; `runner_def`, owner `runner:<name>`). Worker: `prepareRunMCP` writes `<state_dir>/runs/<run>/mcp.json` (0700/0600: operator `mcp_config` + `skopos` with the token, replacing an operator `skopos` entry), `mcpFor(run)` picks it, the token joins `runSecrets` (redacted), removed at run end; a run that came with a token never falls back to the agent key (a failed write = no skopos tools). On a server without authentication a live run token still resolves to its run, not root. Only for a server without run tokens: the agent key (`SKOPOS_AGENT_KEY`), `CheckAgentKey` at startup refuses anything but a capped MCP-only key without approver or admin and with code read; `<state_dir>/agent-mcp.json` = operator `mcp_config` + `skopos`. `agentRun` adds `skoposTools(phase)` for claude/opencode (never codex); prompts include `prompts/skopos.md` via `.Skopos` (`skoposPrompt`, nil = no section); its code part only with `IndexBranch` set by `indexState` (switch on + the server's `/api/codeindex/{ws}/status`: review uses the item branch only when indexed at the reviewed head). Capped keys get `cappedInstructions` in their `initialize` answer.
- Idle-worker indexing (internal/worker/indexer.go): pipeline `code_index` (workspace owners only) → `runs.WorkspacePrefs.CodeIndex`; claims report `indexable` (`workers.indexable`), the answer's `Skopos-Index-Enabled`/`Skopos-Index-Default` headers carry `runs.Service.IndexDuty` (default branch → smallest able worker id). The pass runs in the background while idle (`maybeIndex`, stopped by `stopIndexing` before any run), in `<state_dir>/index/<repo>` (detached worktree), pushing via `codeindex.Push` with the parse cache in `<state_dir>/index-cache`; state in `index-state.json`; item branches indexed at the end of a successful implement, after the push (`indexBranchNow`, bounded 5m, else queued), dropped by the sweep; `pruneStaleIndexes` (default-duty worker, every 6h) drops branches gone from origin (`ls-remote`) and not built for 7 days. The duty skips busy workers (`runs.IndexableWorkers`, the one able-workers query, also behind the pipeline's `indexable_by`); one pass at a time (`indexRunning` — a pass that outlives `stopIndexing` keeps its slot).
- Prompts get the item's brief, not its history (internal/worker/brief.go): `splitItem` (itemtext.Split) cuts the content at the first pipeline heading line (the author's text before it). Plan prompt: brief + questions/answers + `previousPlans` (the round the newest "Review notes" are about) + newest notes. Implement: brief + Q&A + newest approval notes + newest change requests (+ `lastReview` when there are change requests); steps come from the plan revision. A new appended section needs its heading in `itemtext.Headings` (internal/itemtext; `TestPipelineHeadingsCoverWriters` scans the writers). Questions (internal/itemtext/questions.go): the planner returns `questions` as `{question, options}` entries; the worker writes them after the plan as `## Questions — planner[ <label>]`, a numbered list with `   - (a) …` options (`FormatQuestions`/`ParseQuestions`); the implementer's `questions` (amendment/blocked, implSchema; old `question` string still read) go in `## Questions — implementer` (`appendImplQuestions`); `CurrentQuestions` = the newest round's (`Rounds`: the approver's notes close a round) — the Slack gate messages and `skopos inbox plan` list those. Questions and answers are records (internal/qa, tmp/questions-and-answers — design.md, phase 1): STRICT append-only tables `questions` (sets: asker, run, stage, runner, label, subject, blocking) and `answers` (kind answer|general|skipped, action, approval_id, actor, via); state derived in `qa.withState` (answered, answered_free_text, skipped, superseded by the same asker+label, open). The worker posts questions to `POST /api/runs/{id}/questions` (lease-fenced; serve.go's `SetQuestionAsker` records, then `AppendSection` renders the section); an older worker's appended section is recorded from the edit (`ImportAppended`); items from before are imported once at startup (`ImportQuestions`). Approve/request-changes/retry take `answers` (a list by question id, or free text read by `qa.matchText`) through `inbox.prepareAnswers` (checked before any bookkeeping; open questions the gate leaves get `skipped` rows) and `commitAnswers` (after the transition; `answers_matched` on the response); the `## Answers` section is rendered from them (`chainMutations`). `GET /api/inbox/{id}/questions` reads the record. Phase 2: corrections (an answer item with `replaces` = the question's current answer; `qa.current`, `Replaced`/`AfterUse` derived), `POST /api/inbox/{id}/answers` (`inbox.Answer`: approver, awaiting_approval/blocked/failed, no transition, no skipped rows), prompts read the record via `POST /api/runs/{id}/questions/read` (lease-fenced; `qa.ForRun` marks `used_by_run` once, `qa.PromptText` renders; worker `decisions()` falls back to the sections on a 404), Slack `answer:` (never buffered mid-run) and `postMatched` replies, CLI `skopos inbox questions|answer`. Free answers: text given when no question is open is a `general` row with set_id '' (`qa.Record.Free`, in prompts). Import is versioned per item (`qa_imports`, version 2): a version-1 (v0.27.0) item gets its free answers by replaying its import in an in-memory database (`importFree`); any live write marks the item (`recordedLive`) so a restart never replays it. Phase 3: the decision log `qa.Search` (rows per question + free answers, `qa.Filter`) and `qa.Summarize` (total / per workspace / per person), served scoped by `inbox.SearchQuestions` at `GET /api/inbox/questions` (`format=csv`) and `/api/inbox/questions/summary`, the CLI `skopos questions [summary]`, the MCP tool `inbox_questions` (item record or decision log, capped at 200 rows); a live Ask publishes `questions.waiting` (events.Event gained `item` and `data`). REST calls without `X-Skopos-Via` record as `api`; `GET /api/inbox/{id}?parts=1` adds `content_parts` (brief + rounds with `closed`, rendered) for the dashboard's description and answer list.
- Runners (internal/worker/runners.go): agent-CLI agnostic. `claude` and `opencode` adapters have live-verified lockdowns (TestLiveLockdown / TestLiveOpencodeLockdown, opt-in env vars); `codex` (live-verified on macOS: TestCodexLockdownProbe, no tokens, + TestLiveCodexLockdown) is read-only-stage only — `--ignore-user-config --ignore-rules --strict-config`, every setting via `-c`, a permission profile confining shell reads to worktree + git common dir + :minimal (temp dirs closed), no writes/network; refuses implement and any `CODEX_HOME` holding AGENTS.md (no switch for it); stage schemas go through `codexStrictSchema`. `antigravity` (agy) is unverified/wrapper-only (spike: always loads worktree AGENTS.md/GEMINI.md, allowlist only via `$HOME/.gemini/antigravity-cli/settings.json` — the runner rewrites it in the account's login HOME per run — and the first denied tool ends a headless run). `kind = "command"` (any CLI, argv template) is unverified and only runs inside a wrapper. Non-native structured output: schema in the prompt, final JSON extracted + validated. Every agent command gets `PWD=<run dir>` (opencode trusts $PWD — it once committed in the wrong repo). Review worktrees reset instruction/agent-config paths to base before the run. Account `model`/`effort` go to every kind its own way (`effortLevels` + `checkEffort` at config load: claude/agy `--effort`, codex `-c model_reasoning_effort`, opencode `--variant`, command `{effort}` — refused when the template lacks it, and required on every account when it has it); `worker.ValidateEffort` is the one rule (wizard too); `CheckRunner` adds the CLI's effort flag (`EffortSupported`) to the lockdown check when an account sets effort; `AccountWarnings` = one runner's accounts differing in model/effort (warned, not refused).

## Blackboard

Three scopes: `session` (requires `session_id`, cascade-deleted with session via the `blackboard_entries.session_id` foreign key), `branch` (requires `branch_name`), `project` (global).
Six entry types: `finding`, `decision`, `warning`, `context`, `bug`, `debt`.
`bug` and `debt` are "floating" — always included in reads regardless of branch filter.
Read returns both structured `entries` array and a `markdown_bundle` text block.

## Plans

Item statuses: `pending`, `in_progress`, `done`, `blocked`.
`add_dependency` auto-blocks the dependent item. Completing a dependency auto-unblocks dependents.
`remove_dependency` auto-unblocks if remaining deps are all done.
Plan-to-plan dependencies work the same way — adding one blocks the dependent plan, completing the dependency plan auto-unblocks it.

## Database

Schema lives in `internal/db/schema.sql`. On `serve`, `db.RunMigrations(conn.SQL)` runs all CREATE statements. No separate migration files — schema.sql is the source of truth and is re-run with `IF NOT EXISTS`. The DB is file-based SQLite (`skopos.db` by default). Never on a network filesystem (slow commits, WAL corruption risk; serve warns via `db.NetworkFilesystem`): on Nomad the DB lives on the allocation's `ephemeral_disk` and Litestream replicates it to shared storage (`skopos.nomad`, docs/deployment/nomad.md).
